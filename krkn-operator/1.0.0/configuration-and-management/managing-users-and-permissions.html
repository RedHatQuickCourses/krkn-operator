Managing users and permissions

Managing Users and Permissions

The Krkn-operator utilizes a robust, group-based access control model to ensure secure multi-tenant chaos engineering. By decoupling permissions from individual users and associating them with functional groups, administrators can maintain a scalable security posture across multiple Kubernetes clusters.

The Permission Model

The security architecture is built on a hierarchical structure where the Group acts as the primary container for access policies. Every user within the platform must be assigned to at least one group; a user without a group assignment will have no visibility or operational access to the platform.

Key Components

  • Groups: Logical entities created by Administrators that define the scope of interaction. A group configuration specifies:

  • Cluster Accessibility: Which target clusters are available to members.

  • Permissions: The granular operations allowed (View, Run, Delete).

  • Registry Visibility: Which image registries can be accessed by the chaos experiments.

  • Users: Individuals who inherit all permissions associated with their assigned group.

Role Definitions

Permissions are tailored to specific personas within your organization:

Role Responsibilities

Administrator

Manages the infrastructure, registers target clusters, creates groups, maps users to groups, and configures private registries and target providers (such as ACM).

User

Performs operational tasks based on group membership. This includes managing experiment jobs, accessing cluster terminals, executing chaos scenarios, and designing workflows in Chaos Studio.

Operational Capabilities

The scope of a user’s activity is determined by the permissions granted to their group:

  • View and Manage: Ability to observe and interact with existing chaos jobs (requires View/Delete permissions).

  • Terminal Access: Ability to open a shell into a target cluster (requires Run permission).

  • Scenario Execution: Ability to trigger chaos experiments on assigned clusters (requires Run permission).

  • Chaos Studio: Ability to design, modify, and save complex chaos workflows (requires Run permission).

  • File Management: Ability to upload and manage files, scoped strictly by the group’s visibility settings.

Admin Configuration Workflow

To manage the environment effectively, administrators follow this standard lifecycle:

  1. Define the Group: Create a group and designate the specific target clusters that the group will interact with.

  2. Assign Permissions: Select the appropriate permission level (View, Run, Delete) to define the group’s capability on the assigned clusters.

  3. Assign Users: Add users to the group. Upon assignment, the user immediately inherits the group’s security context.

To ensure the principle of least privilege, audit your group assignments regularly. A user’s access is strictly defined by their group—if a user needs access to a new cluster, add that cluster to their existing group or assign them to an additional group with the required access.

Troubleshooting Permission Issues

If a user reports that they cannot see a cluster or execute a command, verify the following:

  • Group Membership: Ensure the user is explicitly assigned to a group.

  • Group Policies: Check if the target cluster is correctly mapped to the user’s group.

Managing users and permissions

The krkn-operator follows a robust, group-based access control model designed to ensure that chaos engineering activities are performed securely and within defined operational boundaries. By decoupling permissions from individual users and attaching them to groups, administrators can maintain consistent security policies across large teams.

The Permission Model

Access in the krkn-operator is hierarchical. Every user must belong to at least one group; a user without a group assignment has no access to the platform’s resources.

Group-Based Permissions

Administrators manage access by creating groups and defining a set of constraints for that group. Each group configuration includes:

  • Accessible Clusters: Defines which target Kubernetes clusters the group can impact.

  • Permissions: Determines the scope of actions allowed (View, Run, Delete).

  • Registry Visibility: Controls which container registries are accessible for pulling chaos experiment images.

Roles and Capabilities

The platform defines two primary roles, each with distinct scopes of responsibility:

Role Capabilities

Admin

Full system control: registers/removes target clusters, creates/manages groups and users, configures private registries, and sets up target providers (e.g., ACM integration).

User

Operational access scoped by group membership: views and manages jobs, executes scenarios, designs workflows in Chaos Studio, and manages files within permitted boundaries.

Every user must be assigned to a group to interact with the system. Without group membership, the user interface will remain restricted, and API calls will be rejected with an unauthorized status.

Operational Scope for Users

When a user is assigned to a group, their operational capabilities are restricted by the permissions granted to that group:

  • View and Manage Jobs: Depends on the View/Delete permissions defined for the group.

  • Cluster Terminal: Requires the Run permission.

  • Scenario Execution: Users can only run chaos scenarios on clusters explicitly assigned to their group.

  • Chaos Studio: Designing and saving workflows requires the Run permission.

  • File Management: Access to upload or manage configuration files is scoped by the visibility settings of the user’s group.

Administrative Workflow

Administrators are responsible for maintaining the security posture of the krkn-operator. The lifecycle of permission management typically follows this flow:

  1. Define Groups: Create a logical grouping (e.g., qa-team, sre-platform) that aligns with organizational structure.

  2. Assign Resources: Map specific target clusters and registries to the created group.

  3. Assign Users: Add users to the groups to grant them the corresponding level of access.

= Managing Users and Permissions

The Krkn-operator utilizes a robust, group-based access control model to ensure that chaos experiments are performed securely and within the boundaries of organizational policy. By decoupling permissions from individual users and assigning them to groups, administrators can maintain consistent security postures across multiple clusters.

== The Permission Model

Access in the Krkn-operator environment is governed by Groups. A user cannot perform any actions on the platform unless they are explicitly assigned to a group.

=== Key Components * Users: Individuals who interact with the Krkn-operator. Every user must belong to at least one group to gain access to clusters, registries, or features. * Groups: Logical containers that bundle access rights. When an Admin creates a group, they define: * Cluster Accessibility: Which target clusters the group can interact with. * Permissions: The level of access (View, Run, Delete) granted to the group. * Registry Visibility: Which container registries are accessible for fetching chaos experiment images.

=== Roles and Responsibilities

There are two primary roles defined within the Krkn-operator framework:

  • Administrator: Possesses full access to the platform. Admins are responsible for the foundational infrastructure, including:

  • Registering and removing target clusters.

  • Creating and managing user accounts.

  • Defining group boundaries and assigning permissions.

  • Configuring infrastructure integrations (e.g., ACM).

  • User: Operates within the scope defined by their group membership. Depending on their assigned permissions, they can:

  • View and Manage Jobs: Monitor the status and logs of chaos experiments.

  • Run Scenarios: Execute chaos experiments on assigned clusters.

  • Chaos Studio: Design and refine workflows (requires Run permission).

  • Terminal Access: Utilize the cluster terminal for troubleshooting (requires Run permission).

Every user must belong to a group. A user without a group assignment will have no access to the platform, ensuring a "secure by default" posture.

== Administrative Workflow

Administrators manage the environment through a hierarchical flow:

  1. Define Groups: Identify the necessary access levels based on project or environment requirements (e.g., prod-admins, qa-testers).

  2. Assign Clusters: Associate specific target clusters with the relevant group.

  3. Assign Permissions: Grant specific capabilities:

    • View: Allows monitoring of existing jobs and cluster state.

    • Run: Allows execution of scenarios, workflow design, and terminal access.

    • Delete: Allows the removal of jobs or experiment artifacts.

  4. Create Users: Provision accounts and map them to the established groups.

When planning your permission model, adhere to the principle of least privilege. Only grant Run permissions to users who strictly require the ability to initiate destructive chaos experiments.
