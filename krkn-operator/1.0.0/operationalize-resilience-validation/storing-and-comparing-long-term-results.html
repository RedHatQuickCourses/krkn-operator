Storing and comparing long-term results

Storing and comparing long-term results

In a mature Chaos Engineering practice, a single experiment provides a snapshot of system health, but long-term data collection provides the "resiliency trajectory." By storing and comparing results over time, you can determine if your platform is becoming more robust or if architectural changes are introducing regression.

The Importance of Historical Data

Chaos experiments should not be treated as ephemeral events. Storing results serves three primary operational needs:

  • Trend Analysis: Identifying if resilience scores are trending upward (improvements) or downward (technical debt accumulation).

  • Regression Detection: Validating that infrastructure upgrades, patch management, or configuration changes have not inadvertently degraded fault tolerance.

  • Compliance and Audit: Providing documented evidence that the system meets Service Level Objectives (SLOs) under adverse conditions.

Strategies for Long-Term Storage

To effectively analyze long-term results, consider these architectural approaches for data persistence:

  1. Centralized Result Aggregation: Use the Krkn Jobs output data to feed into a time-series database (such as Prometheus or Thanos). Ensure that job metadata—such as cluster IDs, scenario versions, and timestamps—is captured as labels.

  2. Versioned Workflow Models: Keep your Chaos Studio workflow definitions in version control (Git). Linking a specific experiment run to a Git commit hash allows you to correlate system performance directly with infrastructure-as-code changes.

  3. Result Normalization: Since Krkn produces detailed logs and metrics, standardize the output format to ensure that comparisons between "Run A" (three months ago) and "Run B" (today) remain statistically valid.

Comparing Results Over Time

When evaluating performance trends, focus on the following comparative metrics:

  • Recovery Time Objective (RTO) Drift: Monitor if the time taken for services to recover from a specific disruption scenario is increasing.

  • Resiliency Score Variance: Track the scores generated by the Resiliency Score feature. A stable score despite increased traffic or complexity indicates successful architectural hardening.

  • Error Rate Correlation: Compare the error rates during chaos events across different months. Decreasing peaks during the same disruption type is a primary indicator of improved resilience.

Hands-on Lab: Analyzing Historical Resilience

This lab demonstrates how to track improvement by comparing results from two different experimental runs.

Prerequisites

  • Access to a Krkn environment with at least two completed chaos workflows.

  • PromQL queries defined for your application’s SLIs.

Step 1: Exporting Historical Run Data

  1. Navigate to the Jobs page in the Krkn dashboard.

  2. Identify two runs of the same scenario (e.g., pod-disruption) executed at different time intervals.

  3. Export the JSON-formatted report for both runs.

Step 2: Comparing Resilience Scores

Using the Krkn CLI or your observability tool of choice, pull the specific Resiliency Score values:

# Example: Retrieving scores for specific job IDs
krkn get-resilience-score --job-id <JOB_ID_OLD>
krkn get-resilience-score --job-id <JOB_ID_NEW>

Step 3: Mapping Trends to Changes

Create a simple comparison table to visualize the improvement:

| Metric | Run (Jan 1) | Run (Mar 1) | Change | | :--- | :--- | :--- | :--- | | Resiliency Score | 72 | 88 | +16 | | Recovery Duration | 120s | 85s | -35s | | Error Spikes | 5% | 1% | -4% |

Self-Check: Analyze if the improvement correlates with a specific infrastructure update or code deployment made between the two dates. If the score dropped, investigate which dependent components experienced increased latency during the latter experiment.

Troubleshooting Tips for Long-Term Comparisons

  • Consistent Baselines: If your baseline traffic changes, your comparison becomes invalid. Ensure experiments are run under similar load conditions to maintain "apples-to-apples" comparisons.

  • Scenario Drift: If you update a scenario (e.g., increasing the number of replicas killed), ensure you tag the experiment with a version identifier so that the comparison takes the change in intensity into account.
