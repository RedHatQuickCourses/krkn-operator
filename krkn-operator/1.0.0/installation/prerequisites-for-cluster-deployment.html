Prerequisites for cluster deployment

Prerequisites for cluster deployment

Before deploying the krkn-operator into your environment, it is essential to prepare your Kubernetes cluster to ensure compatibility, security, and resource availability. Chaos engineering experiments, by design, stress the underlying infrastructure; therefore, a well-prepared foundation is critical for both the stability of your platform and the validity of your chaos results.

Cluster Environment Requirements

To ensure the krkn-operator functions correctly, your environment must meet the following criteria:

  • Kubernetes Version: Ensure your cluster is running a supported version of Kubernetes. Refer to the official Krkn release notes for the specific minimum version required for the operator version you intend to deploy.

  • Permissions: You must have cluster-admin privileges or appropriate RBAC permissions to create Namespaces, ClusterRoles, and Custom Resource Definitions (CRDs).

  • Connectivity: The operator must have network reachability to the API server of the target clusters. If you are utilizing multi-cluster execution, ensure that the communication paths between the management cluster and target clusters are open.

  • Resource Sizing:

  • As noted in our best practices, applications often consume higher resource levels during reinitialization following a crash (e.g., replaying Write Ahead Logs in monitoring solutions like Prometheus).

  • Ensure your worker nodes have sufficient headroom in terms of CPU and Memory to accommodate these spikes during recovery phases. Failing to do so can lead to resource contention that impacts both your application and system-critical pods.

Access and Configuration Prerequisites

Before the installation process begins, ensure you have the following components configured:

Component Requirement

CLI Access

kubectl or oc (for OpenShift environments) must be configured and authenticated against the target cluster.

Helm

The helm binary (version 3.x) is required for deploying the operator charts.

Registry Access

If your cluster resides in a restricted environment, ensure you have access to your private container registries. Configure image pull secrets in the target namespace beforehand to avoid ImagePullBackOff errors.

Namespace Strategy

Determine the dedicated namespace for the operator. While it can be installed cluster-wide, isolating the operator in a specific namespace (e.g., krkn-chaos) is recommended for security and observability.

Best Practices for Chaos Readiness

Beyond technical requirements, consider these operational prerequisites:

  • Node Sizing: Review your node allocation strategies. Chaos experiments should target specific components to understand their behavior under stress. If your nodes are tightly packed with production workloads, ensure that the "fast recovery logic" of your applications is tested prior to executing disruptive experiments.

  • Observability: Confirm that your cluster has monitoring (e.g., Prometheus/Grafana) installed. The krkn-operator leverages PromQL-based metrics for the Resiliency Score feature. Without an active metrics pipeline, you will be unable to measure the impact of your experiments effectively.

  • Isolation: Ensure that the target clusters are clearly identified. If using ACM/OCM integration for automatic discovery, ensure the credentials for those platforms are prepared and verified before attempting to register clusters within the operator interface.

Never execute chaos experiments on a production cluster without first validating the experiment workflows in a staging or development environment. = Prerequisites for cluster deployment

Before deploying the krkn-operator into your Kubernetes environment, it is essential to ensure that your cluster meets the following technical requirements. Proper preparation ensures that the operator functions correctly, especially when interacting with target clusters for chaos orchestration.

== System Requirements

  • Kubernetes Version: Ensure you are running a supported version of Kubernetes (refer to the specific operator release notes for the minimum version, typically the last three minor releases).

  • Compute Resources: The operator and its managed components require sufficient headroom. As noted in our best practices, applications—including the chaos controller itself—may spike in resource usage during initialization or re-recovery cycles.

  • Memory: Ensure your node pools are sized to accommodate the operator pod and any associated monitoring sidecars.

  • Monitoring: If you plan to utilize the Resiliency Score feature, ensure that a Prometheus instance is reachable within the cluster to execute the required PromQL-based metrics queries.

== Permissions and Access

The krkn-operator requires elevated privileges to monitor and manipulate cluster resources.

  • Cluster-Admin Role: The operator requires sufficient RBAC permissions to create, update, and delete resources across the namespaces it manages.

  • Namespace Management: You must decide whether to deploy the operator in a dedicated namespace or a shared one. We recommend a dedicated namespace (e.g., krkn-system) to isolate the operator’s footprint and simplify security auditing.

  • Target Cluster Registration: If you intend to use the Multi-cluster Execution feature, ensure your environment allows network connectivity between the operator cluster and the target clusters. While OCM/ACM integration is optional, it simplifies automatic discovery; otherwise, you must prepare the credentials for manual registration of target providers.

== Network and Connectivity

  • Private Registry Access: If your environment restricts access to public container registries, you must pre-configure the krkn-operator to pull images from your internal private registry. Ensure that the image pull secrets are available in the target namespace.

  • Egress Requirements: The operator needs egress access to any external APIs or private registries required for image retrieval and, if applicable, reporting metrics to your centralized observability stack.

== Best Practice: Planning for Resilience

When preparing your cluster deployment, keep the "Resiliency Score" methodology in mind:

An application pod might use significantly more resources during reinitialization after a chaos-induced crash. Ensure your cluster autoscaler is configured to handle these bursts so that the operator’s activity does not lead to resource starvation for your production workloads.

Before proceeding to the installation phase, verify your current cluster capacity using:

kubectl get nodes
kubectl describe nodes | grep -A 5 "Allocated resources"

= Prerequisites for cluster deployment

Before deploying the krkn-operator into your environment, it is essential to prepare your Kubernetes cluster to ensure compatibility, security, and operational stability. The operator acts as a central control plane for chaos orchestration, requiring sufficient resources and specific permissions to interact with target clusters and manage experiment lifecycles.

== Cluster Environment Requirements

The krkn-operator is designed for Kubernetes-native chaos engineering. To ensure a successful installation, your environment must meet the following criteria:

  • Kubernetes Version: Ensure your cluster is running a supported version of Kubernetes (refer to the specific operator release notes for minimum version compatibility).

  • Compute Resources: The operator platform requires consistent resource availability. As noted in our best practices, monitor your node sizing carefully. Chaos experiments—and the operator itself—may experience spikes in resource consumption, particularly when generating telemetry or managing multiple concurrent experiment jobs.

  • Permissions: You must have cluster-admin privileges (or equivalent rights) to install the operator, manage Custom Resource Definitions (CRDs), and configure necessary Roles/ClusterRoles.

== Network and Connectivity

The krkn-operator excels in multi-cluster environments. To leverage its full capabilities, ensure:

  • Egress Connectivity: The operator requires egress access to container registries to pull the krkn-operator image and related components. If your organization restricts public access, configure your Private Registries ahead of time.

  • Control Plane Access: Ensure the operator has network visibility to the API servers of the target clusters it will manage.

  • Note: While OCM/ACM integration is optional and simplifies automatic cluster discovery, the operator remains fully functional using manual registration of target cluster kubeconfigs.

== Preparation Checklist

Before initiating the Helm installation, verify the following:

Component Requirement

Namespace

Identify a dedicated namespace for the operator to ensure resource isolation.

Helm

Ensure helm (v3.x+) is installed and authenticated with your cluster.

Registry Access

If using a private registry, have your pull secrets ready.

Storage

Ensure the underlying storage class supports the persistence requirements of the operator’s backend database (if applicable for experiment history).

== Best Practices for Stability

Chaos engineering inherently pushes infrastructure to its limits. To ensure the operator does not become a bottleneck:

  1. Node Sizing: Always account for "reinitialization spikes." When an application pod crashes during a chaos experiment, its recovery may require more memory (e.g., replaying write-ahead logs in Prometheus). Ensure your nodes are sized to handle these spikes so the krkn-operator remains stable.

  2. Recovery Logic: Prior to deployment, verify that your target applications possess robust, fast recovery logic. This reduces the risk of cascading failures while the operator manages the experiments.

  3. Isolation: Consider deploying the operator in a separate management cluster or a dedicated namespace with resource quotas (Limits and Requests) to prevent the operator from competing for resources with critical workloads.

Once these prerequisites are met, you are ready to proceed with the namespace creation and Helm-based installation of the krkn-operator.
