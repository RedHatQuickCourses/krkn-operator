Namespace management and creation

Namespace Management and Creation

In the context of the Krkn-operator, namespaces serve as the primary logical boundary for both the operator’s control plane and the scope of chaos experiments. Proper namespace management is critical to ensuring that the Krkn-operator remains isolated, secure, and performant within your Kubernetes environment.

Overview of Namespace Strategy

The Krkn-operator requires a dedicated namespace to host its controller, web interface, and associated backend services. By isolating the operator, you prevent accidental interference with production workloads and ensure that Role-Based Access Control (RBAC) policies can be scoped effectively.

Key considerations for namespace management include: * Isolation: Keeping the operator separate from application workloads. * Resource Quotas: Applying resource limits to the operator namespace to ensure the chaos orchestration platform does not consume excessive cluster resources. * RBAC Scoping: Defining RoleBindings that allow the operator to manage resources in target namespaces without granting cluster-wide administrative privileges.

Managing Namespaces for Krkn-operator

To manage namespaces effectively, follow these best practices for setup and configuration:

1. Creating the Operator Namespace

Before deploying the Krkn-operator, you must create a dedicated namespace. This acts as the home for the operator’s pods.

kubectl create namespace krkn-operator-system

2. Labeling for Security and Integration

If your cluster employs security policies (such as Pod Security Admission), ensure the namespace is labeled correctly to allow the operator pods to run with the necessary privileges.

kubectl label namespace krkn-operator-system pod-security.kubernetes.io/enforce=privileged

Prerequisites

  • A running Kubernetes cluster.

  • kubectl configured with cluster-admin privileges.

Step 1: Create the Operator Namespace

Execute the following command to create the workspace for the Krkn-operator:

kubectl create namespace krkn-operator

Step 2: Verify Namespace Readiness

Ensure the namespace exists and is ready to accept resource deployments:

kubectl get namespace krkn-operator

Step 3: Verify Permissions

As per the permission model, ensure that your administrative user has access to this namespace. If you are integrating this with the Krkn-operator’s web interface later, you will need to map this namespace to a specific user group.

If you intend to run "Namespace Failures" (as defined in our documentation context), be aware that the Krkn-operator will require delete permissions on the target namespaces you designate for experimentation. Ensure your ClusterRole definitions reflect these requirements.

Step 4: Cleanup

If you need to remove the operator and clean up the namespace, use the following command:

kubectl delete namespace krkn-operator

= Namespace Management and Creation

In the context of the krkn-operator, effective namespace management is critical for operational security, resource isolation, and scope definition. By isolating chaos experiments within dedicated namespaces, administrators can prevent unintended "blast radius" expansion during testing.

== Namespace Strategy for Krkn-operator

The krkn-operator follows Kubernetes best practices by utilizing namespaces to segregate the operator’s control plane from the workload clusters and the specific chaos scenarios being executed.

Before deploying the operator, ensure your target clusters have a designated namespace ready to host the controller and its associated resources.

=== Best Practices for Namespace Allocation * Isolation: Deploy the krkn-operator in a restricted namespace (e.g., krkn-system) to separate it from the applications it intends to disrupt. * RBAC Alignment: Since the operator requires permissions to modify objects in target namespaces (like deleting namespaces during a Namespace Failure scenario), use dedicated namespaces to apply the principle of least privilege. * Resource Quotas: When running high-intensity experiments, such as CPU or Memory Hogs, define resource quotas on the target namespaces to prevent the experiment from starving the underlying Kubernetes node.

== Hands-on Lab: Preparing Namespaces

In this lab, you will prepare the environment by creating a dedicated namespace for the krkn-operator and a target namespace for your chaos experiments.

# Step 1: Create the Operator Namespace To begin, create a dedicated namespace to house the krkn-operator installation.

kubectl create namespace krkn-system
kubectl label namespace krkn-system name=krkn-operator

# Step 2: Create a Target Namespace It is recommended to create a separate namespace for testing scenarios. This allows you to safely perform experiments, such as Namespace Failures, without affecting production workloads.

kubectl create namespace chaos-targets

# Step 3: Verify Namespace Status Ensure that the namespaces are active and ready for the operator deployment.

kubectl get namespaces | grep -E 'krkn-system|chaos-targets'

== Managing Permissions per Namespace As outlined in the Permission Model, the Admin must define group access for these namespaces. When configuring users, ensure that the groups assigned to your users include the necessary permissions (View, Run, Delete) for the chaos-targets namespace specifically.

If you are performing a Namespace Failure experiment, ensure the user executing the scenario has sufficient Delete permissions on the target namespace; otherwise, the krkn-operator will be blocked by the Kubernetes API. ====# Namespace management and creation

Namespace Management and Creation

In Kubernetes, namespaces provide a mechanism for isolating groups of resources within a single cluster. For the Krkn-operator, proper namespace management is critical to ensure that chaos experiments are contained, permissions are scoped correctly, and cluster resources are organized effectively.

Why Namespaces Matter for Krkn-operator

When deploying the Krkn-operator, namespaces serve three primary functions:

  1. Isolation: Keeping the operator and its associated chaos experiments separate from application workloads.

  2. Resource Quotas: Preventing a chaos experiment (e.g., a CPU or Memory Hog) from consuming all resources in a production namespace.

  3. Access Control: Allowing administrators to grant or restrict access to specific chaos scenarios based on the namespace where they are deployed.

Creating the Operator Namespace

Before installing the Krkn-operator, you must define a dedicated namespace. This allows for cleaner cleanup procedures and targeted monitoring of the operator’s health.

# Create a dedicated namespace for the Krkn-operator
kubectl create namespace krkn-operator-system

# Verify the namespace was created successfully
kubectl get namespace krkn-operator-system

Configuring Namespace Scope

When managing users and permissions (as defined in the Permission Model), administrators associate groups with specific clusters. However, you can refine this by applying Kubernetes RBAC (Role-Based Access Control) to limit the Krkn-operator’s scope of influence to specific target namespaces.

Best Practices for Namespace Management

  • Principle of Least Privilege: Do not grant the Krkn-operator cluster-admin permissions if it only needs to perform experiments within a specific namespace (e.g., app-staging).

  • Cleanup: When deleting namespaces as part of a chaos experiment (e.g., the Namespace Failure scenario), ensure that the Krkn-operator has the necessary cluster-level permissions to manage those specific objects, while restricting its ability to touch critical infrastructure namespaces like kube-system.

Hands-on Lab: Managing Namespaces for Chaos

In this exercise, you will create a target namespace for your chaos experiments.

  1. Step 1: Create a sandbox namespace

    kubectl create namespace chaos-sandbox

  2. Step 2: Verify Permissions

    Ensure the Krkn-operator service account has permissions to interact with the chaos-sandbox namespace. If you are using the default Helm installation, verify the RoleBinding:

    kubectl get rolebindings -n chaos-sandbox

  3. Step 3: Orchestrate a Namespace Failure

    Once your namespace is prepared, you can target it via the Krkn-operator interface or configuration file to simulate a namespace deletion.

    Ensure no mission-critical applications are running in a namespace tagged for deletion during a "Namespace Failure" experiment, as this operation will remove the namespace and all contained resources for the defined duration.

  4. Step 4: Cleanup

    After the experiment concludes and the namespace is restored, verify the objects:

    kubectl get pods -n chaos-sandbox
