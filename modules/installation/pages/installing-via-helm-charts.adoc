#  Installing via Helm charts

= Installing via Helm charts

The `krkn-operator` is distributed as a Helm chart, facilitating standardized deployments across Kubernetes and OpenShift environments. By leveraging Helm, you can manage the operator lifecycle, perform version rollouts, and customize configurations through `values.yaml` files.

== Prerequisites
Before initiating the installation, ensure your environment meets the following requirements:

* **Kubernetes Cluster:** Version 1.19 or higher, or OpenShift 4.x.
* **Helm:** Version 3.0 or higher must be installed and configured in your local environment.
* **Cluster Access:** `cluster-admin` privileges (or sufficient permissions to create namespaces and CRDs) are required to install the operator.

== Installation Methods

The installation approach depends on how you intend to expose the operator's web interface for scenario orchestration.

[cols="1,2", options="header"]
|===
| Environment | Recommended Access Method
| **Kubernetes** | Gateway API (preferred) or Ingress
| **OpenShift** | Routes (native)
|===

== Quick Start Deployment
For a standard installation using default settings, you can deploy the latest version (v0.4.5-beta) directly from the project's OCI registry. This command automatically creates the necessary namespace and deploys the operator components.

[source,bash]
----
helm install krkn-operator oci://quay.io/krkn-chaos/charts/krkn-operator \
  --version 0.4.5-beta \
  --namespace krkn-operator-system \
  --create-namespace
----

== Production Deployment with Custom Configuration
For production workloads, it is best practice to manage configuration via a custom `values.yaml` file. This allows you to define specific resource limits, replica counts, and exposure methods tailored to your cluster architecture.

1. Create a `values.yaml` file locally:
+
[source,yaml]
----
# values.yaml example
replicaCount: 1
image:
  repository: quay.io/krkn-chaos/krkn-operator
  tag: 0.4.5-beta
# Add environment-specific overrides here
----

2. Deploy the operator referencing your configuration file:
+
[source,bash]
----
helm install krkn-operator oci://quay.io/krkn-chaos/charts/krkn-operator \
  --version 0.4.5-beta \
  --namespace krkn-operator-system \
  --create-namespace \
  -f values.yaml
----

== Verification
Once the Helm command completes, verify that the operator pods are running correctly:

[source,bash]
----
kubectl get pods -n krkn-operator-system
----

== Installation Methods

The Krkn-operator can be deployed using a standard Quick Start method for rapid evaluation or a Production installation for specific ingress/gateway requirements.

=== Quick Start
For testing or demonstration purposes, you can deploy the latest version (v0.4.5-beta) using the default configuration. This command automatically creates the `krkn-operator-system` namespace.

[source,bash]
----
helm install krkn-operator oci://quay.io/krkn-chaos/charts/krkn-operator \
  --version 0.4.5-beta \
  --namespace krkn-operator-system \
  --create-namespace
----

=== Production Installation
In a production environment, you must account for external access to the operator's management interface. Choose the method based on your infrastructure:

* **OpenShift**: Utilize native OpenShift Routes.
* **Kubernetes**: Use Gateway API (recommended) or Ingress controllers.

To customize these settings, create a `values.yaml` file containing your specific networking configurations and install using the following command:

[source,bash]
----
helm install krkn-operator oci://quay.io/krkn-chaos/charts/krkn-operator \
  --version 0.4.5-beta \
  --namespace krkn-operator-system \
  --create-namespace \
  -f values.yaml
----

== Namespace Management
Best practice dictates isolating the Krkn-operator within its own dedicated namespace. The `--create-namespace` flag in the Helm commands above ensures that `krkn-operator-system` is created if it does not already exist. 

NOTE: Keeping the operator in a dedicated namespace prevents resource contention and simplifies the application of RBAC (Role-Based Access Control) policies, ensuring that chaos orchestration remains scoped correctly.

* **Registry Access**: Ensure your cluster has network egress to `quay.io` to pull the OCI chart.
* **Chart Version**: Always verify the latest available version by checking the Krkn-chaos repository, as OCI-based charts are immutable and tied to specific tags.

There are two primary ways to install the Krkn-operator depending on your environment and traffic requirements.

For a standard installation using default settings, you can deploy the latest version directly using the OCI-based Helm chart. This will create the necessary namespace and deploy the operator components.

[source,bash]
----
helm install krkn-operator oci://quay.io/krkn-chaos/charts/krkn-operator \
  --version 0.4.5-beta \
  --namespace krkn-operator-system \
  --create-namespace
----

=== Production Installation with Custom Configuration
In production environments, you will typically need to configure external access to the operator. Depending on your cluster type, the recommended methods are:

* **OpenShift:** Utilize native **Routes**.
* **Kubernetes:** Utilize **Gateway API** (recommended) or **Ingress**.

[source,bash]
----
helm install krkn-operator oci://quay.io/krkn-chaos/charts/krkn-operator \
  --version 0.4.5-beta \
  --namespace krkn-operator-system \
  --create-namespace \
  -f values.yaml
----

== Post-Installation Verification
After running the installation command, verify that the operator components are successfully deploying in the target namespace:

[source,bash]
----
# Check the status of the operator pods
kubectl get pods -n krkn-operator-system

# Check the Helm release status
helm list -n krkn-operator-system
----

[NOTE]
====
If the operator fails to start, ensure that your `values.yaml` configuration is compatible with the version `0.4.5-beta`. Refer to the chart's `README.md` for specific configuration parameters related to authentication and resource limits.
