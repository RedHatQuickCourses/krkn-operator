#  Maintaining operator health

= Maintaining Operator Health

Maintaining the health of the `krkn-operator` is critical to ensuring that chaos experiments are executed reliably without compromising the stability of the management plane. A healthy operator ensures that chaos scenarios are orchestrated correctly, resources are cleaned up post-experiment, and the system remains observable.

== Health Monitoring Best Practices

To ensure the `krkn-operator` functions within expected parameters, consider the following maintenance strategies:

*   **Resource Monitoring:** Monitor the memory and CPU utilization of the `krkn-controller-manager` pods. Excessive resource consumption may indicate memory leaks or an unoptimized reconciliation loop.
*   **Log Analysis:** Regularly inspect operator logs for errors related to API connectivity or permission denials. Using `kubectl logs -n krkn-namespace deployment/krkn-controller-manager` is standard practice.
*   **Condition Tracking:** Leverage Kubernetes status conditions. Ensure the operator reports `Ready` and `Available` statuses. If the operator enters a `CrashLoopBackOff`, investigate the configuration map for syntax errors or invalid experiment parameters.
*   **Event Auditing:** Watch for Kubernetes events within the namespace where the operator is deployed to catch early warnings regarding resource quota exhaustion or RBAC failures.

== Ensuring System Stability

The stability of the operator is intrinsically linked to the underlying cluster health. Apply the following administration standards:

[IMPORTANT]
====
**Machine Health Checks:** Always deploy machine health checks with appropriate conditions to remediate unhealthy nodes. This ensures that even if a chaos experiment targets infrastructure, the cluster maintains enough capacity to run without total downtime, preventing the operator from struggling to reconcile state on degraded hardware.
====

=== Proactive Maintenance Steps

1.  **Reconciliation Audits:** Periodically check the number of active chaos resources. An accumulation of orphaned `ChaosExperiment` custom resources (CRs) can bloat the etcd database and slow down the controller reconciliation loop.
2.  **RBAC Verification:** If you modify service accounts or cluster roles, ensure the operator retains the necessary permissions to interact with target resources. Use `kubectl auth can-i` to verify that the operator's service account has the required verb access (e.g., `list`, `patch`, `delete`) to the target namespaces.
3.  **Dependency Updates:** Periodically verify that the underlying Kubernetes API versions supported by the operator are compatible with your current cluster version.

== Troubleshooting Health Issues

If the operator exhibits unexpected behavior, follow this diagnostic workflow:

. **Check Pod Status:**
+
[source,bash]
----
kubectl get pods -n krkn-operator-system
----
+
. **Inspect Operator Logs:** Look for stack traces or connection timeouts.
+
[source,bash]
----
kubectl logs -n krkn-operator-system -l control-plane=controller-manager --tail=100
----
+
. **Verify Resource Limits:** Ensure that the `LimitRanges` and `ResourceQuotas` in the namespace do not restrict the operator from spawning the necessary pods to execute chaos experiments.

= Maintaining Operator Health

Maintaining the health of the `krkn-operator` is critical for ensuring that chaos experiments are executed reliably and that the operator does not become a bottleneck or a point of failure within your Kubernetes cluster. A healthy operator ensures that chaos scenarios are injected gracefully and that the reconciliation loop functions as expected.

== Monitoring Operator Health

To maintain the operational integrity of the `krkn-operator`, administrators should focus on three primary pillars: observability, resource management, and state verification.

=== 1. Observability and Metrics
The `krkn-operator` exposes Prometheus-formatted metrics that are essential for health monitoring. Use these metrics to create dashboards in Grafana or alerts in Alertmanager:
*   **Reconciliation Errors:** Monitor the `controller_runtime_reconcile_errors_total` metric. A spike here indicates that the operator is struggling to reconcile the state of chaos scenarios against the cluster.
*   **Work Queue Depth:** Ensure the work queue length remains stable. A growing queue suggests the operator is overloaded with pending tasks.
*   **Pod Readiness:** Use standard Kubernetes probes to track the operator pod's status. If the operator enters a `CrashLoopBackOff`, check the logs using:
+
[source,bash]
----
kubectl logs -n krkn-namespace deployment/krkn-operator-controller-manager
----

=== 2. Resource Management
Chaos orchestration can be resource-intensive depending on the frequency and scale of your experiments. 
*   **Resource Limits:** Ensure the `krkn-operator` deployment has appropriate CPU and memory requests/limits defined in its Helm values.
*   **Node Health Checks:** As per best practices, deploy Machine Health Checks within your cluster. If the node running the `krkn-operator` becomes unhealthy, the Cluster API or machine management system should remediate the node to ensure the operator is rescheduled, preventing downtime in your chaos orchestration pipeline.

=== 3. Log Aggregation and Auditing
Regularly audit the operator logs to identify potential issues before they impact production environments. Look for:
*   **Permission Denied Errors:** Often caused by stale `ClusterRoleBinding` or `ServiceAccount` misconfigurations.
*   **Timeout Exceptions:** Verify connectivity between the operator and the Kubernetes API server.

== Proactive Maintenance Strategies

To keep the operator in a stable state, follow these administrative routines:

*   **Cleanup of Completed Scenarios:** Ensure that completed or failed chaos experiment CRDs (Custom Resource Definitions) are cleaned up to prevent etcd bloating.
*   **Regular Version Alignment:** Keep the operator version aligned with your Kubernetes minor version. Using outdated operators with newer K8s APIs can lead to silent failures in experiment execution.
*   **Validation of Service Level Indicators (SLIs):** Periodically verify that your chaos experiments are correctly evaluating your application's SLIs. If an experiment fails to report accurate status, investigate the `Status` field within the chaos CRD.

[NOTE]
====
When failures occur in production, they are costly. Always test your chaos scenarios in a staging environment before deploying the `krkn-operator` to production clusters to ensure that the orchestration logic aligns with your resilience expectations.
====

== Troubleshooting Common Health Issues

|===
| Symptom | Probable Cause | Recommended Action
| High Reconciliation Time | Excessive CRDs in namespace | Cleanup old experiment objects.
| Operator pod flapping | Resource constraints (OOMKilled) | Increase memory limits in `values.yaml`.
| Experiments not triggering | RBAC configuration mismatch | Validate `ClusterRole` permissions for the operator ServiceAccount.
|===

By integrating these health checks into your platform administration routine, you ensure that the `krkn-operator` remains a reliable tool for testing system resilience and identifying weaknesses before they impact end-users.
