#  Handling versioning and releases

= Handling versioning and releases

As the `krkn-operator` evolves to support new Kubernetes primitives and advanced chaos scenarios, maintaining a clear versioning strategy is essential for cluster stability. The operator follows standard software lifecycle practices to ensure that updates do not inadvertently trigger destructive chaos events or interrupt observability pipelines.

== Understanding Versioning Strategy

The `krkn-operator` follows [Semantic Versioning (SemVer)](https://semver.org/), which uses the format `MAJOR.MINOR.PATCH` (e.g., `1.2.4`). This structure allows users to anticipate the impact of an upgrade:

*   **MAJOR version (X.0.0):** Indicates breaking changes. This often involves changes to the Custom Resource Definitions (CRDs) or architectural shifts in how the operator interacts with the `krkn-lib`. Upgrading across major versions may require manual intervention or reconfiguration of existing chaos scenarios.
*   **MINOR version (x.Y.0):** Introduces new features, such as new chaos scenarios or expanded support for cloud-provider-specific disruptions, while maintaining backward compatibility.
*   **PATCH version (x.y.Z):** Focuses on bug fixes, performance optimizations for `krkn-lib` integrations, or security patches. These are generally safe to apply in production environments.

== Release Lifecycle

Releases for the `krkn-operator` are managed through the GitHub repository ecosystem. When a new release is cut, the following artifacts are updated:

1.  **Helm Charts:** The repository's Helm chart version is incremented to match the operator image tag.
2.  **Container Images:** New images are pushed to the container registry, tagged with the specific release version and a `latest` tag (though pinning to specific versions is recommended for production).
3.  **Changelog:** Each release includes a detailed changelog highlighting new features, deprecated items, and fixed issues.

== Best Practices for Upgrades

Before performing an upgrade in a production-grade cluster, we recommend the following workflow:

*   **Review the Changelog:** Always check the release notes for "Breaking Changes." If you are using custom CRDs, ensure they remain compatible with the new operator version.
*   **Use a Staging Environment:** Test the upgrade in a non-production cluster where `krkn-demos` can be run to verify that chaos scenarios execute as expected.
*   **Verify CRD Compatibility:** Since the operator relies on Kubernetes-native objects, verify if the new release requires a `kubectl apply` of new or updated CRD manifests before updating the Helm deployment.
*   **Monitor Operator Health:** Following an upgrade, observe the operator logs for initialization errors. Ensure the `krkn-lib` dependencies are correctly initialized and the operator is able to communicate with the Kubernetes API server.

== Rollback Strategy

In the event that a new version introduces unexpected behavior, the operator can be reverted using Helm:

[source,bash]
----
# List history of releases
helm history krkn-operator -n krkn-namespace

# Rollback to the previous stable release
helm rollback krkn-operator [REVISION_NUMBER] -n krkn-namespace
----

= Handling versioning and releases

In the context of the `Krkn-operator`, managing versions and releases is critical to ensuring cluster stability while benefiting from the latest chaos engineering capabilities. As Krkn matures, understanding how the operator lifecycle aligns with the broader Krkn ecosystem (including `krkn-lib` and `Krkn-hub`) ensures that your chaos experiments remain predictable and repeatable.

== Understanding Krkn Versioning
The Krkn ecosystem follows a structured versioning strategy designed to maintain compatibility across the dependency chain. Because the operator relies on underlying Python functions provided by `krkn-lib`, releases are synchronized to prevent breaking changes during runtime.

*   **SemVer Compliance:** Releases follow Semantic Versioning (MAJOR.MINOR.PATCH).
    *   **MAJOR:** Significant changes to the operator API, CRDs (Custom Resource Definitions), or major architectural shifts.
    *   **MINOR:** New chaos scenarios or features added to the Krkn ecosystem.
    *   **PATCH:** Security updates, bug fixes, or stability improvements for existing chaos experiments.

== Release Strategy and Compatibility
When planning an upgrade, it is important to consider the relationship between the operator and the core Krkn engine. 

[NOTE]
====
Before upgrading the `Krkn-operator`, always verify the version of the `krkn-lib` dependency specified in the release notes. While the operator manages the lifecycle, the core logic resides in the engine; mismatches can result in failed telemetry data or execution errors.
====

=== Best Practices for Releases
1.  **Check the Release Notes:** Always review the GitHub releases page for the `krkn-operator` repository to identify breaking changes in CRD schemas.
2.  **Telemetry Data Integrity:** Krkn outputs telemetry data at the end of runs. When moving between versions, ensure that your post-processing scripts are compatible with any schema changes defined in the new release's `krkn-lib` models.
3.  **Environment Isolation:** If you are using `Krkn-hub` in your CI/CD pipelines, ensure that your environment variables are pinned to specific operator versions to prevent unexpected chaos behaviors during automated testing.

== Identifying Version Information
You can retrieve the current version of your deployed operator using `kubectl`. This is useful for auditing and ensuring your environment is running the expected release.

[source,bash]
----
# Check the image tag currently running in the operator deployment
kubectl get deployment krkn-operator-controller-manager -n krkn-operator-system \
  -o jsonpath='{.spec.template.spec.containers[0].image}'
----

== Upgrade Considerations
When performing an upgrade, the operator lifecycle manager (or manual Helm upgrade) handles the migration of existing resources. However, you should observe the following:

*   **Stateful Experiments:** If a chaos experiment is currently running, avoid performing an operator upgrade. The interruption of the operator's control loop during an active scenario may result in orphaned chaos resources (e.g., pods that were meant to be killed or network latency that was meant to be cleared).
*   **Backup Configs:** Use the File Management capabilities of the operator to export your existing configuration files before applying a version upgrade. This ensures you can revert to known-good configurations if the new version introduces unexpected behaviors.

By adhering to these versioning and release practices, you maintain a robust resilience testing pipeline that is both stable and continuously improving.
