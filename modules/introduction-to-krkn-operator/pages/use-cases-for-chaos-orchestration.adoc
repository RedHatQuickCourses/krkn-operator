#  Use cases for chaos orchestration

= Use cases for chaos orchestration

Chaos orchestration is the systematic practice of injecting controlled failures into a system to verify its resilience against the inherent uncertainties of distributed environments. By leveraging the **Krkn-operator**, teams can move beyond manual testing and transition into automated, repeatable resilience validation.

== Why Chaos Orchestration Matters

Distributed systems often fail due to assumptions that rarely hold true in production, such as the reliability of the network or the infinite availability of shared resources. Chaos orchestration addresses these by proactively challenging the system’s design.

=== Key Use Cases

Through the Krkn-operator, you can implement the following strategic use cases:

[cols="1,3"]
|===
| Use Case | Description

| **Validation of High Availability (HA)**
| Simulate the loss of individual nodes or pods to ensure that orchestration layers (like Kubernetes) correctly reschedule workloads and that service traffic reroutes without user-facing downtime.

| **Dependency Resilience Testing**
| Inject network latency or packet loss between microservices to evaluate how application code handles timeouts and circuit breaking. This ensures that a degradation in one component does not trigger a cascading failure across the entire system.

| **Resource Exhaustion Profiling**
| Artificially induce memory or CPU spikes on specific deployments. This helps verify that Horizontal Pod Autoscalers (HPA) trigger correctly and that the application behaves gracefully under load rather than crashing unexpectedly.

| **Resiliency Score Benchmarking**
| Use the Krkn-operator to measure your system against a "Steady State." By defining critical SLOs (e.g., API server latency), you can quantify how much your system's performance degrades during an experiment, providing a measurable **Resiliency Score**.

| **Automated Compliance Verification**
| Integrate chaos experiments into your CI/CD pipelines to ensure that every release maintains the required reliability standards before being promoted to production.
|===

== Mapping Chaos to Business Goals

Chaos orchestration is not just about breaking things; it is about validating the *corrective* mechanisms built into your architecture. 

* **Defining the Steady State:** Before orchestration begins, you must establish the "normal" behavioral baseline. Without this, you cannot objectively measure the impact of an experiment.
* **Analyzing Metrics:** During orchestration, the Krkn-operator allows you to monitor key KPIs. By comparing these against your established steady state, you can identify "blind spots" where monitoring or alerting might be insufficient.
* **Continuous Improvement:** Use the data gathered from orchestrated experiments to prioritize architectural changes. If an experiment proves a service is not resilient, the output provides the specific data needed to justify remediation efforts to stakeholders.

Chaos orchestration is the practice of systematically planning, executing, and automating the injection of faults into a distributed system to validate its resilience. By using tools like the `krkn-operator`, teams move beyond manual, ad-hoc testing toward a continuous, integrated resilience strategy.

== Why Orchestrate Chaos?

In complex Kubernetes environments, individual components often behave correctly in isolation, but fail under the pressure of interconnected dependencies. Chaos orchestration addresses this by enabling teams to move from reactive troubleshooting to proactive resilience modeling.

=== Key Use Cases

[cols="1,3", options="header"]
|===
| Use Case | Description
| **Validation of SLOs/SLIs** | Verify that Service Level Objectives (SLOs) remain intact during component failure. Orchestrating chaos helps determine if automated recovery mechanisms (e.g., auto-scaling, self-healing pods) trigger within the required timeframes.
| **Resilience Score Benchmarking** | Measure the "Resiliency Score" of an application by observing how metrics (such as API latency or request success rates) fluctuate during orchestrated fault injection.
| **Dependency Failure Analysis** | Test how an application handles the loss of shared resources, such as database connectivity, service-to-service communication timeouts, or localized network partitions.
| **Recovery Time Objective (RTO) Testing** | Quantify the time required for a service to return to its steady state after a synthetic failure, ensuring compliance with business continuity requirements.
| **Drift and Configuration Validation** | Confirm that infrastructure-as-code (IaC) configurations and Kubernetes resource limits actually perform as intended when the system is under duress.
|===

== Chaos Workflows: Serial vs. Parallel Execution

A core benefit of chaos orchestration within the Krkn ecosystem is the ability to design **Visual Chaos Workflows**. These workflows are not merely single-command executions; they are structured experiments:

*   **Serial Execution:** Used for validating cascading failures. For example, testing the impact of a database outage followed by a secondary network latency spike to see if the recovery process for the first failure is interrupted by the second.
*   **Parallel Execution:** Used to simulate "stress" scenarios or multi-vector attacks, such as injecting high CPU utilization across multiple worker nodes simultaneously to observe the behavior of the Kubernetes scheduler and cluster-autoscaler under collective pressure.

== Integrating Chaos into the Lifecycle

Orchestrating chaos is most effective when it is integrated into the software development lifecycle:

1.  **Steady State Definition:** Before orchestrating, you must define the "steady state." This involves baseline performance metrics (e.g., request latency, error rates, throughput).
2.  **Hypothesis Injection:** Select a component and hypothesize its behavior under failure. For example: *"If I terminate a core service pod, the redundant replica will take over traffic within 5 seconds without user-visible latency spikes."*
3.  **Automated Orchestration:** Use the `krkn-operator` to execute the experiment. By orchestrating this, you ensure consistency—the experiment is performed the same way every time it is triggered, allowing for accurate comparison of results over different software versions.

= Use cases for chaos orchestration

Chaos orchestration is the practice of automating, scheduling, and sequencing chaos experiments to move beyond simple, manual fault injection. By leveraging the **Krkn-operator**, teams can move from ad-hoc testing to continuous resilience verification.

== Why Chaos Orchestration Matters

In a distributed system, individual components often appear healthy, but failures emerge when dependencies interact under stress. Orchestration allows you to model these complex interactions, ensuring your system remains resilient against the "fallacies of distributed computing," such as network latency, partition events, and resource exhaustion.

By using the **Chaos Studio** interface within the operator, you can move from executing isolated tests to building robust scenarios that reflect real-world production incidents.

== Core Use Cases

=== 1. Validating Resilience to Network Instability
Distributed systems rely on the assumption that the network is reliable. Chaos orchestration allows you to:
* **Simulate Latency:** Gradually inject latency between services to determine the impact on your SLOs.
* **Network Partitioning:** Test how your application handles split-brain scenarios or intermittent connectivity between nodes.
* **Packet Loss Injection:** Verify if your retry logic and circuit breakers successfully mitigate packet loss before they impact the end user.

=== 2. Testing Resource Saturation and Auto-scaling
A common point of failure is when services consume unexpected amounts of resources. Orchestration allows for:
* **Resource Exhaustion:** Intentionally spiking CPU or memory usage on specific pods to see if Horizontal Pod Autoscalers (HPA) trigger as expected.
* **Dependency Stress:** Measuring how your application behaves when a shared database or cache resource becomes unavailable or throttled.

=== 3. Measuring Resiliency Score
The Krkn-operator provides the ability to calculate a **Resiliency Score**. Orchestration is critical here because:
* It allows for the execution of a defined "steady state" measurement before, during, and after the chaos injection.
* By orchestrating scenarios, you can compare the current system performance against pre-defined SLOs, providing a quantifiable metric for improvements made to the system's architecture.

=== 4. Automated Recovery and Self-Healing Validation
Rather than just breaking things, orchestration is used to verify that the system recovers without manual intervention.
* **Scenario Chaining:** You can design a workflow where a pod is killed, and the operator tracks the time taken for the replacement pod to become "Ready" and receive traffic.
* **Serial and Parallel Execution:** Create complex dependencies by running experiments in series (e.g., kill a node, then induce network latency) or in parallel to simulate a "cascading failure" scenario.

=== 5. Continuous Resilience in CI/CD
Chaos orchestration enables the integration of resilience testing into your deployment pipeline. By using the Krkn-operator’s configuration, teams can:
* Automatically trigger a set of "sanity check" chaos experiments whenever a new version of a service is deployed.
* Use the web interface to visualize these workflows, ensuring that resilience is a shared, visible metric across development and operations teams.

[IMPORTANT]
====
Before orchestrating any scenario, always ensure you have established a clear **steady state**. Without defined metrics for success, you cannot effectively analyze the impact of the injected chaos or iterate on your infrastructure's improvements.
