#  Overview of Kubernetes-native Chaos Engineering

= Overview of Kubernetes-native Chaos Engineering

Kubernetes-native Chaos Engineering is the practice of proactively injecting controlled failures into a Kubernetes environment to identify weaknesses in system resiliency. By systematically disrupting components—such as killing pods, inducing network latency, or exhausting resources—you can observe how your applications and infrastructure react under stress.

The primary goal is to shift from reactive firefighting to proactive design, ensuring that your systems can gracefully recover from failures before they impact end-users.

== The Role of Krkn-operator

In the context of the Kraken (Krkn) ecosystem, the **Krkn-operator** serves as the control plane for orchestrating these experiments within a Kubernetes cluster. Unlike manual script execution, the Krkn-operator provides a structured, automated way to lifecycle-manage chaos experiments.

=== Core Pillars of Krkn Chaos Engineering

*   **Observability-Driven:** Integration with PromQL-based metrics allows you to measure the impact of chaos in real-time, providing a "Resiliency Score" for your applications.
*   **Automation:** By moving away from manual `kubectl` commands, the operator allows for the definition of reusable, version-controlled chaos scenarios.
*   **Safety and Control:** The architecture is designed to allow granular permission management, ensuring that chaos experiments are scoped strictly to intended targets.
*   **Multi-Cluster Orchestration:** Chaos is rarely isolated to a single node. The Krkn-operator architecture supports executing experiments across multiple clusters, simulating real-world regional outages or large-scale control plane issues.

== Why Kubernetes-Native?

Traditional chaos engineering tools often operate at the infrastructure level (e.g., shutting down virtual machines). Kubernetes-native chaos engineering, facilitated by the Krkn-operator, focuses on the orchestration layer:

1.  **Abstraction of Complexity:** Through tools like `krknctl` and the operator-based web interface, users do not need to manage the underlying container runtime complexities.
2.  **Kubernetes Resource Awareness:** Experiments understand Kubernetes primitives. For example, a scenario can target a specific `Deployment` or `StatefulSet` rather than just a random IP address, ensuring the experiment maintains semantic relevance to your application architecture.
3.  **CI/CD Integration:** Because chaos scenarios are defined as reproducible configurations (or container images within the `krkn-hub`), they can be treated as first-class citizens in a CI/CD pipeline, allowing developers to test resiliency as part of the standard deployment process.

== Architectural Components

*   **Krkn-hub:** A repository of pre-built container images containing specific chaos scenarios.
*   **Krkn-operator:** The controller that watches for Chaos Custom Resources (CRDs) within your cluster, triggering the execution of scenarios from the hub.
*   **Chaos Studio:** A management layer that enables the design of complex workflows (serial or parallel execution) and monitors the health of the target cluster during the experiment.

By integrating chaos experiments directly into the Kubernetes lifecycle, we ensure that:

= Overview of Kubernetes-native Chaos Engineering

Kubernetes-native Chaos Engineering is the practice of proactively injecting controlled failures into a Kubernetes environment to identify and mitigate weaknesses before they impact end-users. By intentionally inducing faults—such as pod terminations, network latency, or resource exhaustion—teams can validate the resiliency of their applications and the self-healing capabilities of the underlying cluster.

== Why Chaos Engineering Matters
In distributed systems, failures are inevitable. Infrastructure components, network partitions, and application bugs are common occurrences. Relying solely on manual testing is insufficient because it often fails to account for the complex, emergent behaviors that arise in highly dynamic environments like Kubernetes.

Chaos engineering shifts the focus from "testing for success" to "testing for failure," allowing SREs and developers to:
* **Validate Auto-scaling:** Ensure your cluster scales correctly when a node is suddenly terminated.
* **Verify Health Checks:** Confirm that liveness and readiness probes accurately detect and recover from unstable application states.
* **Measure Mean Time to Recovery (MTTR):** Observe how quickly your system restores service after a failure occurs.
* **Build Confidence:** Shift from reactive troubleshooting to proactive system hardening.

== The Krkn Approach
Krkn is designed to be Kubernetes-native, meaning it leverages standard Kubernetes primitives to orchestrate chaos. Unlike legacy tools that require custom agents or complex sidecar injection, Krkn treats chaos scenarios as first-class citizens within the cluster ecosystem.

The Krkn ecosystem consists of several components that simplify this workflow:

* **Krkn-hub:** A repository of pre-packaged, containerized chaos scenarios. These scenarios are designed to be run as standard Kubernetes jobs, allowing you to use existing CI/CD pipelines and infrastructure tools to trigger tests.
* **krknctl:** An orchestration layer that abstracts the complexity of manual configuration. It manages the lifecycle of these chaos jobs, allowing users to focus on defining the blast radius and success criteria rather than runtime management.
* **Chaos Studio:** Provides a visual interface to manage workflows, enabling users to chain multiple scenarios together in serial or parallel sequences to simulate real-world, cascading failure scenarios.

== Core Concepts
Understanding the following concepts is essential for effective chaos orchestration:

* **Blast Radius:** The scope of the cluster impacted by the experiment. In Krkn, this can be limited to specific namespaces, labels, or nodes.
* **Steady State:** The measurable baseline behavior of your system under normal conditions. Before injecting chaos, you must define what "normal" looks like (e.g., latency under 200ms, 99.9% success rate).
* **Observation:** Using tools like PromQL to monitor the system throughout the experiment. Krkn integrates with Prometheus to measure the "Resiliency Score," quantifying how well your application maintains its steady state during a fault injection.

By embedding these practices directly into your Kubernetes workflow, you transition from simply deploying applications to engineering resilient, self-healing platforms.
